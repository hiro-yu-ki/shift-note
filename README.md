## 最初の起動

前提: **Windows、Node.js 24 LTS、Python 3.13 64bit（Python Launcher の `py` を含む）**。初回の依存パッケージ取得にはインターネット接続が必要です。導入後の通常利用には外部サービス・APIキーは不要です。

PowerShellで実行します。

```powershell
cd 'C:\Users\micro\product\バイトのシフト'
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

未セットアップなら依存関係導入、DBマイグレーション、フロントエンドビルドを実行します。ブラウザで **http://127.0.0.1:8000** を開いてください。終了は起動したターミナルで `Ctrl+C`。

明示的なセットアップ・更新:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup.ps1
```

最初に管理者パスワード（10文字以上）を設定します。給与・管理APIはログイン必須です。従業員は専用URLから本人画面を利用します。

初回画面で店舗名、営業時間、週の起点曜日、表示単位を設定できます。「デモデータで試す」はスタッフ14名・2週間の期間・提出済み12名・下書き1名・未提出1名を作ります。初期役割はホール、キッチン、レジ、責任者です。デモの初回自動生成は「シフト案」から行います。

## 操作の流れ

1. **スタッフ**: 役割、週の希望・最低・上限、期間上限、最短勤務、日上限、連勤、勤務間隔、固定の勤務不可を登録。資格が必要な業務は役割として登録してください。保有スキル欄は記録用です。
2. **期間を作成**: 1〜31日の開始・終了・締切を設定。前期間の曜日条件を複製可能。期間編集で日ごとの営業時間・休業と、同じ時間に勤務してほしい組み合わせを設定できます。
3. **必要人数・役割**: 曜日と時間帯別の必要人数・役割内訳を設定。15分・30分（初期値）・60分の枠を作成可能。役割人数を必須にすると不足時の確定を禁止します。特定日の条件は、その日の曜日テンプレート全体を置き換えます。合計人数は常にソフト条件です。
4. **希望の提出状況**: スタッフごとに提出URLを発行。「スタッフ画面を開く」で本人用画面を確認できます。URL再発行は旧URLを無効にします。未提出のみの絞り込みと店長による代理入力も可能です。
5. **スタッフ画面**: 日ごとに時刻と勤務可能／できれば入りたい／勤務不可を入力。複数時間帯、終日不可、前日コピー、曜日まとめ設定、一時保存・提出・締切前の再提出に対応。未入力時間は勤務不可です。
6. **シフト案**: 方針を選び、事前確認のあと3案を作成。14名・2週間ではこの検証環境で通常数十秒程度。PC性能と条件で変動します。
7. カレンダーの時間枠をクリックし、対象の勤務を選んで編集。スタッフ別一覧も利用できます。変更は保存時に必ず再検証され、直前の1操作を取り消せます。
8. 不足・希望外・時間上限などを確認し、確定者名を入力して確定。重大違反がある案は確定できません。合計人数の不足などの確認事項は残したまま確定可能です。
9. スタッフ本人用画面で確定シフトを確認。店長は全体のCSV・印刷を利用できます。確定解除時には確認ダイアログが出ます。

表からの貼り付けはタブ区切りの「曜日番号（0=月〜6=日）、開始、終了、合計人数」です。既存の条件に追加され、重複する行は拒否します。役割内訳は個別編集で指定します。

## データと安全性

- SQLiteファイルはプロジェクト直下の **`shift.db`**。通常利用の再読み込み・再起動で保持されます。
- バックアップはサーバー停止後に `shift.db` をコピーしてください。稼働中のファイル単体コピーは避けてください。
- 状態はSQLAlchemy管理の店舗スナップショットに保存。希望・期間・役割・勤務・警告などは型検証されたJSON集合、共有トークンと監査履歴は別テーブルです。AlembicでDB構造を管理します。
- 更新はSQLite内のバージョン比較で競合を検出。競合時は自動上書きせず、再読み込みを案内します。
- 提出URLは256bitのランダム値を使い、DBにはSHA-256ハッシュだけを保存。URLのフラグメントから専用ヘッダーで送り、通常のアクセスURLにトークンを含めません。起動スクリプトではアクセスログを無効化しています。
- スタッフ用APIは対象の本人・期間だけ返し、他人への提出、締切後、確定後、無効なURLを拒否します。店長の代理入力は締切後も可能ですが確定後は不可です。
- **同一PC内のローカルMVPです。管理者パスワード認証を実装しています。LAN・インターネットへ公開する構成ではありません。** 別端末での運用にはHTTPS・配信環境・バックアップ運用の整備が必要です。スマホ幅のUIはこのPCのブラウザで検証できます。
- CORSを開放せず、HostとOriginをローカルに限定。CSVは数式として解釈される先頭文字を無害化し、Excel向けUTF-8 BOM付きで出力します。
- スタッフの削除は履歴保護のため無効化です。参照されている役割は削除できません。

## 自動作成の考え方

- 自動作成は**店舗設定の15分・30分・60分単位、1日1つの連続勤務、勤務中は1役割**です。入力・検証・求解・カレンダーを同じ単位に統一しています。複数役割を持つ人も同時刻に2役割として数えません。
- 勤務不可、営業外、固定不可、日・週・期間上限、最短・最長勤務、間隔、連勤、資格をハード制約にします。別期間の確定済み勤務も週上限・日上限・勤務間隔・連勤へ反映します。
- 人数不足、優先希望、希望時間との差、最低希望時間、勤務時間の偏り、週末・繁忙枠（必要5人以上）の負担、任意の組み合わせにペナルティを設定します。希望・最低時間はソフト条件です。
- 必須役割を満たすモデルが不可能と判定された場合だけ役割不足を緩和し、最善努力の案として表示。重大な役割不足は残り、確定を止めます。勤務不可や時間上限は緩和しません。
- まず充足可能な解を探索し、その解を初期値にして改善。探索時間内の実行可能解であり、常に最適と証明するものではありません。`UNKNOWN`は探索上限による未確認で、不能の証明ではありません。
- 方針の重み・探索量は `backend/engine.py` に集約。1ワーカーと決定的探索量制限を使用し、同じ入力・seed・依存バージョンで再現します。
- 充足率＝必要人数枠に対する充足人数枠、希望一致率＝「できれば入りたい」枠への割当比率、公平性＝期間換算した希望時間との差の標準偏差。公平性は小さいほど希望との差の偏りが少ないことを表します。

## よくある問題

- `ortools` が見つからない: 32bit Pythonでは導入できません。`py -0p` で確認し、Python 3.13 64bitを入れてください。アプリは `.venv64` を使用します。
- `8000`/`8001` が使用中: 同じアプリやE2Eサーバーを二重起動していないか確認してください。通常利用は8000、E2Eは8001です。
- 設定が画面に反映されない: `scripts/setup.ps1` で再ビルドし、サーバーを再起動してください。
- 「他の画面で更新」: 再読み込みしてから入力をやり直します。上書きを防ぐため意図的に停止しています。
- 「確定済みに影響する変更」: スタッフ・役割・基本営業時間の変更は既存の確定シフトにも影響します。関係する確定期間を再編集に戻してから変更してください。
- 解がない／人数不足: 事前検査と警告詳細で必要役割、提出状況、時間上限を確認してください。人数不足と重大違反は区別して表示します。
- pytestでStarletteのhttpx移行予告が表示される場合があります。現固定バージョンではテスト成功を確認しています。

既知の制約と次の改善点は `HANDOVER.md` を参照してください。

## 勤務条件・休憩・自動作成の改善

スタッフ編集では、基本の曜日・時間帯（優先／限定）、最早出勤・最遅退勤、週の最大日数、期間の最低希望日数を追加できます。「限定」や出退勤の制限は必須、最低希望日数・希望時間数は目標です。基本パターンは提出済み希望との共通部分だけに使います。従業員は未入力日にパターンを読み込み、確認して提出できます。基本パターンだけで勤務可能とはみなしません。

文章条件は「読み取る→結果を確認→勤務条件へ反映→スタッフを保存」の順です。対応する書式は画面内に表示します。不明な行はエラーにし、未確認の文章があれば自動作成を止めます。備考と任意追加項目は記録用で、自動作成の制約ではありません。文章から変更した項目も最終保存で数値・参照・矛盾を検証します。

AIで自由な日本語を読み取る機能は任意です。サーバー環境に `OPENAI_API_KEY` と Structured Outputs 対応の `SHIFT_AI_MODEL` を設定して再起動すると選択できます。キーはブラウザに保存・表示しません。実行時に条件文をOpenAIへ送ることを画面で確認します。スタッフ一覧・提出希望全体・登録された給与情報は送信せず、選択した条件文だけを送ります（文章に個人情報を書けばそれも含まれます）。氏名等は除いてください。AIは形式への変換を提案するだけで、勤務を直接保存しません。API未設定・通信失敗・曖昧な条件は自動反映しません。この環境では外部AIを呼ばず、応答の代替データで境界を検証しています。

休憩は `店舗設定 → 勤務途中の休憩` で追加ルールと出退勤からの余白を設定します。標準の下限は実働6時間超で45分、8時間超で60分。休憩は15分単位で勤務途中に置き、なるべく中央を優先します。個別契約の追加休憩も反映。勤務上限を満たす目的で設定にない長い休憩を作ることはありません。休憩中は必要人数・役割人数に数えず、給与と日・週・期間の実働時間から除きます。提出時間外・勤務日以外・勤務の先頭や末尾には置きません。勤務開始・終了は店舗の15/30/60分単位です。

既存の古い案には休憩を勝手に挿入しません。「条件更新済み」の表示が出るため再作成してください。確定済みの案を変更するときは再編集に戻します。契約履歴の有効期間管理・実勤怠・割増賃金・給与の正式計算は引き続き対象外です。

自動作成は、勤務日時・資格・休憩・実働上限等を制約として守りながら、人員充足・本人の希望・割当の偏り・登録時給・交通費・余剰配置を評価します。3案は比較用の実行可能解であり、全員の希望達成や最安費用を証明するものではありません。時給未登録は比較用に登録者の中央値、全員未登録なら1,200円を仮定し、給与見込みでは未登録と表示します。0時間の人には提出状況・最短勤務・資格・需要との重なり等の確認理由を表示します。

作成は背景処理として進捗を表示し、同じブラウザの再読み込み後も状況を確認できます。生成中に希望・設定が変われば競合で保存を止め、以前の案を維持します。計算不能や時間切れを空の成功案として保存しません。同じ条件では保存済み案と手動調整を再利用します。

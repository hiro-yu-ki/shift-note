# シフトノート 1.2 公開・運用手順

## Windowsで先にメール認証を試す

送信専用Gmailの2段階認証とアプリパスワードを用意し、`powershell -ExecutionPolicy Bypass -File scripts/configure-gmail.ps1` を実行します。秘密値はチャットに貼らず、この対話入力にだけ入力します。Windowsユーザー単位で暗号化して `%LOCALAPPDATA%/ShiftNote/mail.xml` に保存します。画面手順は `/help/email.html` です。

次に管理画面のログイン管理で本人の受信先を登録し、`/employee` からコードを要求して実際に受信確認します。送信設定前の内容確認には管理者専用の従業員画面プレビューを使えます。クラウドではローカルの暗号化ファイルを使わず、以下のSMTP環境変数を設定します。


## 概要

単一店舗向けです。管理者は `/admin`、従業員は `/employee` を使います。URLは別ですがデータは同じサーバーで管理し、APIで権限を分離します。従業員のメールとスタッフIDは一対一です。管理画面のファイルを見られても、管理APIには管理者認証が必要です。

推奨構成は **Render の Docker Web Service + 永続ディスク + TLS対応SMTP**。OR-ToolsのPython処理を維持し、HTTPSとサーバー運用を委ねます。1 CPU / 2 GBを初期候補とし、実データで生成時間・メモリを確認して調整します。Cloudflare Workersの通常実行環境へPythonのネイティブ最適化処理をそのまま移す構成は採用していません。DNSをCloudflareで管理している場合は独自ドメインのDNSだけに利用できますが、追加契約は必須ではありません。

**公開状況：公開用のコードと設定一式です。クラウド上の公開・実メール到達・課金契約は未実施です。** このPCでの検証と本番環境での受入確認は別です。既存の店舗DB、メール、秘密情報は配布ZIPに含めません。

## 始める前に

- Renderアカウントを用意します。公開用コードは https://github.com/hiro-yu-ki/shift-note に配置します。有料サービスと永続ディスクの料金は作成前に管理画面で確認します。費用の契約は所有者が行います。
- メール認証の利用開始前にTLS対応SMTPを用意します。Gmailは公開準備の前提ではありません。送信元のアカウント・ドメイン確認と実メール受信は、従業員へURLを配布する前に済ませます。受信者のメールはログイン時に送信サービスへ渡ります。
- 管理者と運用担当者を決めます。本版は管理者パスワード1つの構成で、複数管理者の個別権限・MFAは未実装です。
- 原則、新しい空のDBから本番スタッフを登録します。ローカルの架空データは本番へコピーしません。

## 1. 公開環境を作成する

1. RenderのGitHub連携で `hiro-yu-ki/shift-note` を選びます。リポジトリには `.env`、DB、バックアップ、仮想環境、テスト用のメール捕捉コードを含めません。
2. RenderのBlueprint作成でそのリポジトリの `render.yaml` を指定します。1インスタンスで使用してください。SQLiteと計算ジョブは複数インスタンス・複数ワーカー対応ではありません。
3. Blueprintが公開URLと安全な乱数を設定します。秘密値はRenderの環境変数欄で管理し、Gitやチャットに貼りません。初回デプロイ時にGmail設定は不要です。

| 変数 | 設定 |
|---|---|
| `SHIFT_ENV` | `production`（Blueprintで設定済み） |
| `SHIFT_DB` | `sqlite:////data/shift.db`（永続ディスク） |
| `SHIFT_PUBLIC_ORIGIN` | BlueprintがRenderの `RENDER_EXTERNAL_URL` から設定。独自ドメインに切り替える場合はBlueprintと一緒に更新 |
| `SHIFT_AUTH_SECRET` | Blueprintで生成。確認コードの保護に使用 |
| `SHIFT_SETUP_TOKEN` | Blueprintで生成。管理者初回設定キー |
| `SHIFT_SMTP_HOST` | メールの利用開始前にRenderのEnvironmentで追加。Gmailなら `smtp.gmail.com` |
| `SHIFT_SMTP_PORT` | メールの利用開始前に追加。Gmailなら `465`（暗黙TLS） |
| `SHIFT_SMTP_USER` | メールの利用開始前に追加。Gmailなら送信元メールアドレス |
| `SHIFT_SMTP_PASSWORD` | メールの利用開始前に追加。Gmailならアプリパスワード。通常のGoogleログインパスワードは使わない |
| `SHIFT_MAIL_FROM` | メールの利用開始前に追加。Gmailなら送信元メールアドレス |

4. 初回公開URLは `https://サービス名.onrender.com` に自動設定されます。独自ドメイン利用時は `render.yaml` の公開URL設定をそのHTTPSオリジンに変更し、再デプロイします。別ホストでのアクセスは拒否されます。
5. デプロイを実行します。起動時に設定検証、DBマイグレーション、Webサーバー起動の順で処理します。`/healthz` が `status: ok` を返すことを確認します。
6. `https://公開ホスト/admin` を開き、初回設定キーと管理者パスワードを入力します。キーがない人は最初の管理者になれません。パスワードは運用担当者本人が設定してください。
7. 店舗の初回設定を行います。実運用では「デモデータで試す」をオフにして、実際のスタッフと契約を登録します。

ドメイン変更時は `SHIFT_PUBLIC_ORIGIN` も更新します。クロスオリジン許可やワイルドカードHostを追加して回避しないでください。公開版ではSecure Cookie、同一オリジン検査、フレーム埋め込み禁止を有効にし、従来の無記名トークンURLは無効にします。APIアクセスログは起動時に無効化します。

## 2. メール認証と配布を確認する

1. RenderのEnvironmentへ上記SMTP 5項目を追加します。送信元を持っていない場合はGmailの2段階認証とアプリパスワードを設定します。公開先ではWindowsの `mail.xml` は使われません。次に自分で受信できるテスト用メールを、テストスタッフに登録します。本人が確認するまで他人のアドレスを使わないでください。
2. 管理者と異なるブラウザまたはシークレットウィンドウで `/employee` を開きます。
3. コード送信・受信・ログイン・本人名・対象期間を確認します。コードは8桁・10分有効・使い捨て、5回失敗で失効します。メールごとに60秒間隔、1日20回、全体で1時間200回の制限があります。過剰操作は429になります。
4. 希望を入力・提出し、管理者画面でその人の提出だけが更新されたことを確認します。
5. ログアウト、再ログイン、メール変更後の旧ログイン失効、利用停止、他者データ非表示を確認します。
6. 本番スタッフを登録し、共通の従業員URLと `employee.html` を配布します。メール登録だけでは招待メールを送りません。従業員が「確認コードを送る」を押した時点で送信します。

送信設定の「設定済み」は必要な環境変数が存在するという意味です。実際の接続・送信元認証・受信箱到達は上記の実送信で必ず確認します。未登録アドレスにも同じ画面メッセージを返します。SMTP障害の場合も登録有無を明かさず、サーバーログに宛先を含まない警告を出します。認証はメール受信者本人の識別であり、多要素認証ではありません。

## 3. バックアップ・更新・復元を行う

SQLiteの稼働中コピーには同梱のバックアップスクリプトを使います。Render Shellで例：

```sh
python scripts/backup.py /data/backups/shift-2026-09-26.db
```

新規ファイルにオンラインバックアップし、整合性を検査します。日々および更新直前に取得し、**サーバー外のアクセス制限された保存先にも保管**します。同じディスク内だけではディスク消失に備えられません。自動外部バックアップはこの版では未設定です。DBには給与・メール・セッション等が含まれます。一般のファイル共有リンクで配布しないでください。

更新は、バックアップ→別環境で新しいイメージとバックアップのコピーを起動→動作確認→手動デプロイの順です。永続ディスクを使うデプロイには停止時間があります。計算中は更新しないでください。再起動すると進行中の計算ジョブは失われますが、保存済み案は保持されます。

復元は、サービス停止→現DBを別名で保全→バックアップを `/data/shift.db` に配置→ファイル所有者をアプリ実行ユーザー（UID 10001）へ合わせる→起動→整合性・件数・ログイン・提出を確認、の順です。停止中に扱うため、Shellが使えない場合は永続ディスクを扱える運用手順をホスティング側と確認してください。バックアップ内のセッションを復活させないため、復元コピーでは `manager_session`、`employee_session`、`email_challenge` を空にしてから起動してください。ダウングレードで既存DBを消す操作は行いません。古いアプリへのロールバックは更新前DBのコピーとセットで検証します。

復元準備には `python scripts/restore_copy.py バックアップ.db 新しい復元先.db` が使えます。原本を変更せず、新しい復元コピー内の管理者・従業員セッション、確認コード、旧提出リンクを無効にします。現在稼働しているDBを出力先に指定しないでください。

公開URLが確定したら、開発フォルダで `python scripts/make_release.py --public-origin https://公開ホスト` を実行すると、従業員用ZIPに実際のURLとショートカットを含めて再生成できます。公開前のZIPは手順書のみで、利用可能な外部URLを含みません。

## 4. リリース受入チェック

- [ ] HTTPS、実ドメイン、永続ディスク、再起動後のデータ保持
- [ ] 本人が管理者パスワードを設定し、初回設定を第三者が行えない
- [ ] 実メール到達、誤コード、再利用、期限切れ、再送間隔
- [ ] 管理APIを従業員から取得できず、本人以外の給与・希望が見えない
- [ ] 希望の提出・再提出、締切後拒否、確定後表示
- [ ] 実際のスタッフ規模で3案生成、休憩、提出時間内、必要人数、時給・人件費
- [ ] スマホとPC、印刷、CSV
- [ ] 利用停止とメール変更で旧セッションが使えない
- [ ] バックアップ取得、別環境で復元、外部保管
- [ ] テスト用スタッフを無効化し、実運用担当者が確認
